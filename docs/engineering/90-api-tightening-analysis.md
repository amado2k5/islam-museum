# 90 — API tightening: analysis and design (Phase 1, analysis only)

Status: **proposal, awaiting the founder's approval.** Nothing in this document has been implemented. No API behaviour, file, path or build step was changed by the pull request that added it.

Asked by the founder in chat on 28 November 2026. Written by Claude (`claude-sonnet-5-5`) in a Claude Code session, from the code at commit `c48518e51ee` and from a local run of the API export on this machine (`npm run graph`, the two time-browser scripts, `npm run derive`, `npm run api`, all exit 0; 89,102 entities exported). Nothing was deployed and no hosted address was tested; the only live-site facts used are those already recorded in the repository's own traffic evidence (`docs/analytics/traffic-evidence-2026-11-24.md`).

**The data is not being restricted.** The Founder's Charter promises free use of the museum's data, and data stays CC0, prose CC BY-SA 4.0. This design changes only the *shape* of the public API: whole-corpus access moves to the dataset releases (GitHub release assets, archived by Zenodo), which stay complete and CC0. Section 6.1 records one gap that must be closed *before* any bulk file leaves the API: today the releases do **not** contain the graph dumps.

## 0. Summary of findings

1. The API is generated by one script, `scripts/export-api.ts` (`exportApi`, lines 1048–1145), plus one Astro route (`site/src/pages/api/v1/meta/index.json.ts`) and one deploy-time stamp (`api/v1/meta/deploy.json`, written by `.github/workflows/deploy-env.yml:260` and `deploy-shared-env.yml:289`). A local run wrote **153,392 files, 3.7 GB**.
2. About **1.2 GB of it is unscoped**: two full-graph dumps (`graph/nodes.ndjson` **240 MB**, `graph/edges.ndjson` **19.7 MB**), 30 per-class `index.json` files (**251 MB**; `passage/index.json` alone 86.5 MB), and 88 whole-feature files at the API root (**723 MB**; `ulama.json` 77.6 MB, `ibadat.json` 68.0 MB, `ansab.json` 60.3 MB). Outside the API host, the whole-map search synonym files `search-synonyms.<lang>.json` (five files, 93–110 MB each) are also unscoped.
3. **No page of the website, in any language, fetches any of these unscoped files.** The only visitor-time API reads are small and already scoped: `meta/deploy.json` and `meta/counts.json` (every page, shell script), `meta/search-canon.<lang>.json` (search and graph pages), the single-entity neighbourhood `graph/<class>/<slug>.json` (graph explorer), and single entities `<class>/<slug>.json` (Shelf and My Tour). The games read nothing from the API.
4. The unscoped files are *published* — printed as links on ~50 browser pages, listed in `llms.txt`, the developers page, the OpenAPI spec, the cite page's JSON-LD — so their consumers are external: developers, AI readers, crawlers. Removing them is a public-contract change, not a site change.
5. **Cost reality (stated plainly, because the brief rests on it):** removing or sharding the bulk files saves little in R2 Class A writes. The bulk set is about 130 files; even when all of them change and the large ones go up in multipart parts, that is a few hundred Class A operations per deploy, against 6.84 million in the November period. The November writes came from HTML churn (164,000 pages; `AGENTS.md`, "Keep deploys small"). The real savings of this tightening are bytes stored and served, deploy time (one 240 MB direct upload per deploy, `workers/r2-sync/batch/publish.mjs:96`), memory risk in the sync Workers, and the scraping load the bulk files invite. Section 5 gives the numbers.
6. **Recommended design (section 7):** keep every already-scoped path unchanged; replace each unscoped file by a small manifest at the same path plus stable, criterion-keyed shards beside it; move the two graph dumps and the whole-map synonym files to the dataset release; keep `llms.txt` exactly as it is in the first step (it is a site discovery file, not an API file) and decide its split separately. UAT first; rollback is a re-deploy of the previous build.

## 5. Cost model: R2 Class A writes per deploy

R2 bills Class A per write operation. The publisher writes only files whose SHA-256 changed (`publish.mjs`, manifest diff); files over 20 MB go up directly with the S3 tool, which splits them into multipart parts (each part is a Class A operation; the AWS CLI default part size is 8 MB).

- **Bulk set today:** 2 dumps + 30 class indexes + ~80 large feature files + 5 whole synonym maps ≈ **117 files, ~1.5 GB**. Almost all of them change on any content change within their scope (any new passage rewrites `passage/index.json`, `nodes.ndjson` and every feature file that lists passages). Worst case per deploy: ~117 PUTs + multipart parts ≈ 1.5 GB / 8 MB ≈ 190 parts → **roughly 300–450 Class A operations per deploy**, and ~1.5 GB of upload.
- **For comparison:** November's 6.84 M Class A writes, about $27 (AGENTS.md); one whole-site HTML rewrite is ~164,000 writes. **The bulk API files are well under 1% of the write bill.** Tightening the API is justified by bytes, deploy time and memory risk (the 162 MB `nodes.ndjson` already stopped a UAT deploy, `publish.mjs:96–98`), and by the scraping load whole-corpus files invite — not by Class A cost. This contradicts an implicit premise of the brief and is reported as such.
- **Sharding's own cost:** a shard keyed by a *stable* criterion (class, section, slug prefix) changes only when a record in it changes, so a deploy rewrites a few shards instead of one giant file: Class A count stays about the same or falls slightly, bytes fall sharply. **Offset pagination** (page N of a sorted list) is the opposite: one insertion shifts every later page, so every page is rewritten — **more** Class A writes than today. Pagination by offset is therefore rejected.

## 6. Options

### 6.1 Prerequisite for every option that removes a bulk file

The dataset release must carry the compiled graph before the API stops serving it: attach `nodes.ndjson`, `edges.ndjson` (and, if wanted, the class indexes and feature files as one archive) to each GitHub release as assets, so Zenodo archives them. Today the release is the git tree only, and the compiled dumps are gitignored. Releases are made by hand; the founder decides whether a workflow attaches the assets (a workflow that only builds and attaches files is not a deploy, but it is a new publication path and needs his word).

### Option 1 — Leave as is, document the scope (e)
- **Changes:** nothing in the API; the developers page and OpenAPI mark A3/A4/A5/A6 as "bulk, may move".
- **Breaks/risks:** none. The 240 MB dump keeps growing toward the sync's limits; scraping load stays.
- **Class A:** unchanged (~300–450 per deploy for the bulk set).
- **Verdict:** not recommended; does not meet the brief.

### Option 2 — Remove the bulk files outright (a)
- **Changes:** stop writing A3, A4, A5, A6 and S1.
- **Breaks:** `lib/numbers.ts:28` (build); the cite page JSON-LD; ~50 printed links on browser pages; ~89 `llms.txt` links; the developers page and OpenAPI contract; every external client. Visible change: dead links on browser pages — violates "nothing user-visible changes".
- **Class A:** saves the ~300–450 per deploy and ~1.5 GB upload.
- **Verdict:** rejected.

### Option 3 — Manifest at the old path, stable shards beside it (c), dumps to the release (recommended)
- **Changes:** each unscoped path keeps answering with a small manifest (≤ ~50 KB): `{ "feature", "generated", "total", "shard_by", "shards": [{ "key", "href", "count" }], "dataset": <release URL> }`; the records move to shards keyed by a stable criterion:
  - A3 `<class>/index.json` → `<class>/index/<k>.json`, keyed by the first character of the slug (ASCII slugs: 36 keys max; passage by work, see below).
  - A6 `<feature>.json` → `<feature>/<section>.json` using the section/corpus field each feature already computes (`section`, e.g. quran / sunnah / seerah / books, `export-api.ts:1309, 1325`), and for features without one, by the record's class; the subject index (`subjects`) stays in the manifest when small, else `<feature>/subjects.json`. Any shard still over a cap (proposed 5 MB) is split again by slug prefix.
  - `passage/index.json` → by `work` (the passage's source book), split by slug prefix above the cap.
  - A4/A5 → removed from the API after 6.1 is done; `graph/nodes.ndjson` and `graph/edges.ndjson` paths answer with a manifest pointing to the release asset and to the class-sharded indexes. (A file named `.ndjson` holding a JSON manifest is a content-type surprise; alternative: keep the path as a 301 to the release asset. Founder's choice, see 7.)
  - S1 whole synonym maps → not published (the shards S2 stay); the whole map goes into the release archive.
- **Breaks/risks:** external clients that read records directly from an old path get a manifest (unknown count; section 3.5 check). `lib/numbers.ts:28` must count from the graph instead (a build change, same commit). OpenAPI, developers page, `llms.txt` descriptions and the cite page JSON-LD change text (all seven languages for the developers page). Shard keys must be computed in one place and tested.
- **Class A:** about the same file count changes per deploy as today, fewer bytes; the 240 MB direct upload disappears. Net: a small fall, from ~300–450 to an estimated ~150–300 per deploy (most shards untouched by a typical content batch). Not a material saving on the bill; a material saving in upload (≥1.2 GB less per content deploy) and in failure risk.
- **Nothing user-visible:** the ~50 printed links still resolve (to the manifest); no page fetches any of these files.

### Option 4 — A Worker in front of the API answering queries
- **Changes:** a Worker on `api.islam.museum` that reads shards and answers `?class=&q=&page=`.

- **Verdict:** not recommended; breaks "the architecture stays static" without need.

### Option 5 — Offset pagination of every bulk file (d)
- **Changes:** `<feature>/page/<n>.json`, fixed N records.
- **Class A:** **higher** than today (section 5: every insertion shifts all later pages).
- **Verdict:** rejected.

## 7. Recommended design

**Option 3, in four steps, each its own pull request, each proven on UAT before production:**

1. **Release carries the dumps** (6.1): the next GitHub release attaches `nodes.ndjson`, `edges.ndjson` and an archive of the class indexes, feature files and whole synonym maps. Zenodo then archives them as part of the dataset, CC0. No API change yet. *Founder decision: by hand or by a release-asset workflow.*
2. **Add shards and manifests alongside, change nothing old:** the exporter writes `<class>/index/<k>.json`, `<feature>/<section>.json` and a `manifest` field set, while the old whole files stay as they are. OpenAPI and the developers page document the new paths. `lib/numbers.ts` counts from the graph. Fully additive: zero risk to any consumer.
3. **Switch the old paths to manifests** (A3, A6) and drop S1 and the two dumps (A4/A5 paths answer with a manifest or a 301 to the release asset — *founder decision*). Migration notes in the developers page (seven languages), OpenAPI (`deprecated` + description), `docs/data/README.md`, `llms.txt` descriptions and CANARY (**Breaking**, major version bump by `docs/engineering/15-release-notes-and-versioning.md`).
4. **`llms.txt`: leave as it is.** It is a site discovery file, not the API; it lists pages, not data. Whether to split it into per-class files is a **separate founder decision**, with the loss stated: unmeasured, because no repository evidence says how AI readers use it.

Everything already scoped — A1, A2, A7, A9–A12, S2, S4, S5 — is untouched in every step. The website, the explorers, the games and UAT see no change (section 3: none of them reads a file this design changes, except `lib/numbers.ts` at build time, fixed in step 2).

**Rollback:** every step is a normal build; rolling back is the founder re-running the deploy with the previous `build_run_id` (`deploy.yml` input), which republishes the previous files exactly by hash (`publish.mjs` manifest diff writes the old bytes back and deletes the new shard keys). UAT first: deploy step N to UAT, run section 8, then production.

**Submission impact:** the Zenodo record and the DPGA/UNESCO dossiers describe the API and its "isDerivedFrom" link (`53-scholarly-record.md:24`). Step 3 changes what that link serves. Label step 3 **submission-impacting** (`docs/ai-change-gates.md`); the wording in the dossiers is checked before it lands.
