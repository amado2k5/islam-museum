# islam.museum: instructions for every agent

This file is the single entry point for every AI agent, model, tool or human collaborator working on this repository, whatever the vendor, product or model. `CLAUDE.md`, `GEMINI.md`, `.kiro/steering/`, `.github/copilot-instructions.md` and `.cursor/rules/` are one-line pointers to this file; edit rules here and nowhere else.

islam.museum is an open, free, all-digital museum of Islam: the faith, civilization, peoples, places, ideas, objects, texts and living culture, from the world Islam was born into until today. It is a knowledge graph in git (`data/<class>/<slug>.yaml` for language-neutral facts, `content/<lang>/<class>/<slug>.md` for prose) published as a static site.

   Then `docs/ai-change-gates.md`, binding on every agent: no edit without an approved written proposal, stay in scope, label anything that could alter a filed submission (DPGA, UNESCO) as submission-impacting, three-way merge before every push, the quality and content gates restated, attribution trailers, and the no-go registry of reserved areas.

## Rules that never bend

- **Golden set (founder rule, 8 November 2026 — decision record dec-20261108-188).** Everything currently in the museum — all data, prose, events, persons, books — is the golden reference. Rules and the decision engine are calibrated to it, never the reverse: if a rule would rule out an existing entity, the rule is wrong and gets fixed, not the content. New rules apply forward; existing published content is never retroactively invalidated.
- **Static, no AI at runtime.** Static site on Cloudflare (since 18 October 2026). There is no live fallback mirror (founder's decision, 13 November 2026: a Cloudflare outage is accepted and the site is rebuilt from git if ever needed; the options to revisit are in `docs/engineering/06-deployment.md` section 5a). **Hosting split (founder rule, 28 October 2026): Cloudflare Pages holds code and logic only; data, content, maps, images, pictures and video go to Cloudflare R2**, served by the site Worker (`workers/site/src/route.js` `R2_DATA_DIRS`, published by `workers/r2-sync/batch/publish.mjs`). A new folder of data or media is added to those two lists (a root-level data file such as a sitemap or favicon to `R2_ROOT_FILES` and `ROOT_FILES`), to `run_worker_first` in `workers/site/wrangler.production.toml` and to the exclude list of the assets-only step in `deploy-env.yml`, never left on Pages; no servers, no databases, no paid services beyond hosting. Models are used only in the building phase; nothing on the published site calls a model or any server code per visitor (`docs/plan/03-architecture.md` §13, ADR 0002). Astro + Svelte islands + Tailwind; TypeScript scripts; Pagefind; MapLibre + PMTiles; Sigma.js.
- **Graph in git.** IDs are `class/slug`, immutable; renames go through `aliases`. Relations use `schema/predicates.yaml` only; write each edge once (inverses are computed). Reuse before you create; a duplicate becomes an alias of the richer entity.
- **Sources.** Every entity cites sources; one source is enough for any fact, dated or not. Wikipedia and Wikidata are sources for entity facts (URLs, websites, author names, book names, locations, dates and identifiers) when the fact is taken from a recorded revision, cited, and recorded in the authenticity ledger (`docs/delegation/wikipedia-broad-rule-proposal.md`). They are never sources for prose, for the content of a work, or for the validity of a text. Validation does not expire; it is reaffirmed on review. Never invent a date, quote, page number, ISBN or citation. Dates: EDTF + Hijri string + calendar + precision; conversions marked derived.
- **Arabic first, English and Urdu always** (`docs/language.md`). Arabic is written first: `label.ar` and `summary.ar` are required, and new prose goes in `content/ar/`. From 18 October 2026, every new prose file, UI string, menu item and component also ships with its English (`content/en/`, `i18n/en.yaml`) and Urdu (`content/ur/`, `i18n/ur.yaml`) translation in the same commit, marked `status.review: draft` with a `provenance` block (AI output is draft-tier until a human reads it — see below). Any agent from any vendor follows this; a change that cannot include its translations says so in the commit and progress file.
- **Voice and scope.** A warm, precise, neutral docent: describe, never prescribe, no rulings, no sermon voice. Sunni Islam is the default and main frame, and research starts from Sunni sources (`docs/scope.md`); any other view is welcome and must be labelled before it is stated. Contested topics use the `perspectives` block: Sunni position(s) first, then the academic view, then any other view, each cited and labelled, no verdict. Never write "enemy of Islam" or an equivalent in the museum's voice: describe the act and attribute the judgement. A person's faith is recorded only with its basis, never inferred. Opponents, critics and allies are included with time-scoped `story_roles`. Hard questions are tension cards with at least two cited voices and no verdict.
- **HARD BLOCK: no content about, from or sympathetic to terrorist organisations (founder rule, 7 November 2026, every agent from every vendor).** The museum contains **no mention** of the organisations and propaganda wings below, in any language, in any class (data, prose, sources, media, stubs, summaries, notes). Never cite, quote, link, summarise, name or reproduce them or their material, and never add a page, event card, film card, biography or source whose subject or publisher is one of them. This is a hard block, not a style guide: if a task would require it, stop, say so, and do not write the item. Where a historical topic is valid but a source carries modern extremist framing, drop the framing and rewrite from an academic, art-historical or archaeological angle; if a person's documented life cannot be told without the group, write the fact neutrally ("an armed group", "militants") or leave the sentence out. Also refuse extremist vocabulary hijacking classical terms (the rhetorical register of Dabiq or Inspire). **Blocked organisations:** ISIS / ISIL / Daesh / Islamic State and affiliates (ISIS-K, ISWAP, Boko Haram, Abu Sayyaf); Al-Qaeda and affiliates (AQAP, AQIM, AQIS, Al-Shabaab, Al-Nusra Front / Hay'at Tahrir al-Sham, Hurras al-Din); Hamas (Qassam Brigades), Hezbollah, Palestinian Islamic Jihad, Harakat al-Nujaba, Kata'ib Hezbollah; Taliban, TTP, Lashkar-e-Taiba, Jaish-e-Mohammed, Haqqani Network, Harkat-ul-Mujahideen, Indian Mujahideen; Jemaah Islamiyah, GIA, Al-Jama'a al-Islamiyya, Ansar al-Sharia, Ansarullah Bangla. **Added 14 November 2026 from the official designation lists (EU, US State/OFAC, Canada, UN, UK, Australia, New Zealand):** Abdallah Azzam Brigades, Al-Murabitoun, Al-Muwaqi'un Bil Dima, Asbat al-Ansar, Al-Ittihad al-Islamiya, Caucasus Emirate, Egyptian Islamic Jihad, Islamic Jihad Group, Islamic Jihad Union, Eastern Turkistan Islamic Movement, Ummah Tameer-e-Nau, JNIM, Ansaru, Ansar Bayt al-Maqdis, Jund al-Aqsa, Jund al-Khalifa, MUJAO, Macina Liberation Front, Jaysh al-Muhajirin wal-Ansar, Harakat al-Sabireen, HASAM, Al-Ashtar Brigades, Fatemiyoun Division, Hezb-e Islami Gulbuddin, the Lebanese Muslim Brotherhood (designated chapter), IRFAN-Canada, Lashkar-e-Jhangvi, Hizbul Mujahideen, Islamic Movement of Uzbekistan, Jemaah Anshorut Tauhid, Jammat-ul-Mujahideen Bangladesh, Islamic Army of Aden. **Ruled in full by the founder on 14 November 2026:** Ansarallah / the Houthis, the Islamic Revolutionary Guard Corps (IRGC), Ansar Dine, Hizb ut-Tahrir, Ansar al-Islam, the Sudanese Muslim Brotherhood (designated chapter) — no propaganda material about them, supporting them or from them in any record, past, existing or future; their surviving neutral mentions are the founder-approved exceptions, and the Al-Andalus Media pattern alone awaits the founder's ruling on one ambiguous record — full record and classification sources in `docs/agents/content-safety.md` section 2. **Blocked media:** Amaq, Al-Hayat Media Center, Al-Furqan, Al-I'tisam, Naba, Dabiq, Rumiyah, As-Sahab, Al-Malahem, Al-Andalus Media, Al-Kataib Media Foundation, Az-Zallaqa, Inspire, Al-Manar (Hezbollah), Al-Aqsa TV (Hamas); these change URLs, so block by publisher name, not by address. **Not matches (never remove):** Marj Dabiq, Tafsir al-Manar, Hudayr al-Kata'ib, "al-Shabab" meaning youth or the football club, "taliban ilm" meaning students, the Qur'anic "hizb Allah", the 1992 Islamic State of Afghanistan, the generic "Islamic state", "Ibn Hamas", and Hitti's *Origins of the Islamic State*. `npm run validate` enforces it (`scripts/check-extremism.ts`): the build fails on any mention outside the exceptions list. Full rule and decision record: `docs/agents/content-safety.md`. **Founder-approved exceptions:** the records listed in `docs/delegation/extremism-firewall-exceptions.md` were reviewed one by one on 7 November 2026 and kept; never delete or trim them to remove a mention, and never treat them as precedent for adding new content about a blocked organisation. The audit, the manifest and the change report are in `docs/delegation/extremism-firewall-*.md`.
- **Arabic parentheses are isolated (rule of 6 November 2026, every agent and session).** Arabic text is right-to-left, so a plain `(` or `)` inside an Arabic string is mirrored and lands on the wrong side of the phrase. Wrap every parenthetical that contains Arabic script as `\u2066(...)\u2069` (LEFT-TO-RIGHT ISOLATE U+2066, then the parenthesis, the text, the closing parenthesis, then POP DIRECTIONAL ISOLATE U+2069). This applies to everything written or imported: prose, data labels, names, summaries, UI strings, and anything harvested, ingested, OCR'd or copied from a source. Write `⁦(` and `)⁩` directly as those characters in the file, not as escape text. Do not wrap parentheses that hold no Arabic. Existing parentheses are converted in the staged replacement; new content must already follow the rule.
- **No honorifics typed anywhere** (not ﷺ, not «صلى الله عليه وسلم», «عليه السلام», «رضي الله عنه», «رحمه الله»): the UI renders them. The validator rejects them.
- **Qur'an text is never typed, completed or corrected.** It comes only from the frozen Tanzil files and is referenced as `[[passage/quran-<sura>-<aya>|label]]`. The validator rejects ﴿ ﴾ in prose.
- **Prose only in `content/<lang>/<class>/<slug>.md`; data only in `data/<class>/<slug>.yaml`.** Never a `.yaml` under `content/`.
- **Licences.** Prose CC BY-SA 4.0, data CC0, code MIT. Third-party content keeps its own licence. Media only from the whitelist in `schema/enums/licenses.yaml`; no figurative depictions of prophets or Companions; no AI-generated portraits. **Sources** (`docs/sources-policy.md`, founder's standing rule of 15 Oct 2026): any source may be read, copyrighted or not, and its content rewritten in the museum's own words with a citation to the source and page; facts enter `data/` from any source. What stays out of git: verbatim text beyond a 40-word cited quotation, the source files themselves (PDFs, OCR text, page images, claims tables, dumps) and un-whitelisted media.
- **AI output is draft-tier until a human reads it (founder ruling, 8 November 2026 — decision records dec-20261108-152/161, confirmed 2026-11-08).** All AI-generated prose and machine translations enter as `status.review: draft` with a `provenance` block (`generated_by`, `model`, `run`, `source`) once they cite defined sources (`docs/agents/publication-standard.md`): they go live only after a human read promotes them to `published` — no agent may self-promote AI output. One source is still enough for any fact once published. `draft` here is a review state, not a judgement on quality. An illustration that passes the automated gates of `docs/agents/lanes/illustrations.md` section 3 may be marked approved by the pipeline, recorded with `status.approved_by: "pipeline"` and the gate report hash.
- **Every feature is graph, API and search (founder rule, 6 November 2026).** Every browser, explorer, class or feature, present and future (the Time Browser, the Job Browser, the Inventions Browser, the Fatwa and Khutab explorers, the poetry anthology, the Screening Room, the Modern Islam Browser and whatever comes next), keeps its records in the one graph as classes and kinds with registered predicates (never a side table or a second graph), is exported in the static API (the class exports plus its own `/api/v1/` files, documented in `docs/data/README.md`, `site/public/openapi/v1.json` and `llms.txt`), and is indexed by search (its records as entity pages; its landing page's title, lede and headings through `data-pagefind-body`). It is also documented in the register `docs/site/browsers.md`, the plan index, the roadmap, `docs/agents/lanes.md` and `docs/status.md`. Full rule and checklist: `docs/site/browsers.md`.
- **Accessibility.** WCAG 2.2 AA; alt text required; no JS needed to read a page.
- **Checks before you push.** `npm run validate` (0 errors) and `npm test` (all pass); `npm run build` for any site change. Fix what fails; never lower a rule, skip a test or add a crash guard to hide bad data.
- **Harvest register (founder rule, 14 November 2026).** Before any download, OCR, harvest, mining or ingestion, look the item up in `docs/library/harvest-register.yaml`; if it is there and not deleted, use that state and never redo finished work; update the entry in the same PR when a state changes. A book may be deleted from the microSD only when its entry says complete and the deletion gate in `docs/library/README.md` is met (OCR zip verified first).
- **Enrichment register (founder rule, 14 November 2026).** When your queue is empty or you finish early, take work from `docs/library/enrichment/` (`npm run enrichment-queue`: missing Wikidata and other ids, missing or partial prose, wanted records, weak sources, missing dates and coordinates); claim it in `docs/library/enrichment/claims.yaml` in your first commit, mark it done when merged; never start an item another agent has claimed.
- **Keep deploys small.** A deploy uploads every file whose bytes changed, and a line baked into every page changes all ~164,000 of them (about 30 minutes and 19 GB). Put nothing that changes often (a version, a date, a count) in a layout or in a component the layouts import, and keep page scripts in plain files under `site/public/shell/`, not inline. The compiled stylesheet is inlined into every page on purpose (linking it fails the Lighthouse gate, `docs/engineering/16-deploy-churn-proposal.md`), so a `site/src/styles/` edit is a whole-site rewrite too. The files baked into every page are listed in `tools/deploy/shell-paths.list`; a pull request that touches one is labelled `rewrites-all-pages`, and the founder batches those into one deploy a week. Details: `docs/site/README.md` ("site-wide numbers").
- **Canary release notes.** Every change — feature, fix, modification, removal, performance improvement, test, data change, breaking change, rollback — appends its entry to `CANARY.md` in the same commit, under the current version block, grouped by kind and written for readers (what changed and why it matters, never a bare commit message). A change without its canary entry is not finished and does not merge. A rollback gets its own entry naming what was reverted and why; history is never rewritten. The site version shown in the footer and on the changelog page is read from the top of `CANARY.md` at build time; bump it by `docs/engineering/15-release-notes-and-versioning.md` (breaking → major, new feature, page, class or endpoint → minor, fixes and corrections → patch).
- **Canary workflow — how every agent ships a change.** (1) Make the change. (2) Update `CANARY.md` in the same working tree: append the entry under the current version block, grouped by kind; if the change bumps the version, open the new block on top with the new version and today's date. This applies to *every* change, including docs-only, config, workflow and `AGENTS.md` changes themselves. (3) Run the gates: `npm run validate` (0 errors), `npm test` (all pass), `npm run build` for any site change, and regenerate `docs/coverage.md` in the same commit when entities changed. (4) Commit explicit paths only (never `git add -A`), with the `AI-Agent:` / `AI-Model:` / `AI-Editor:` trailers. (5) Fetch `origin/main` first; if it moved, 3-way merge your work with what landed — never overwrite another agent's work, never force-push. Push your branch and open the pull request; agents merge their own PRs once the gates pass — but only after fetching `origin/main`, reviewing what landed, and three-way merging so nothing is overwritten (founder ruling, 8 November 2026 — decision record dec-20261108-185, which narrows dec-20261108-160). Finished work is never left uncommitted or unpushed. (6) Report accurately afterwards: merged is not live — deployment is the founder's manual step, so name the merged PR and say the change goes live at his next deploy.

## Working together (details in `docs/agents/workflow.md`)

- **Rich first pass, for every topic.** Write the full, detailed prose and as many well-sourced details as the sources allow in the first pass, for any entity: a person, a book, an article, a building, an object, a place, an event, a concept, a practice. Do not leave enrichment for later runs or phases. Enrichment happens at the start, and later work is revision only. Mark an item as a lead only when it is genuinely unverified, not because it was left for later. Full rule: `docs/agents/content-standards.md`.

- **Act as the human in the loop (founder delegation, 8 November 2026).** The founder delegates to the agent everything a human owner was expected to do, decide and answer. Work like a person who owns the outcome, not a tool that executes a step: understand the whole situation before acting — what is really being asked, what is at stake, what could go wrong; generate the real options, research them when needed (acquire books, corpora, web sources; set and record your own criteria for which sources to trust); weigh consequences and side effects, second-order effects and reversibility; choose; execute; then follow up — verify the outcome actually happened, check for regressions, close the loop, and feed what you learned back into rules, precedents and criteria. Do not stop at the mechanical minimum when the situation clearly needs judgment, and do not ask the founder what you can responsibly determine yourself — but record every judgment in the decision ledger (`docs/decisions/inbox/` → `decide.ts` → record) with question, evidence, options, rationale, verdict and reversibility, so the founder can audit asynchronously. Trust criteria an agent invents are recorded in the lane progress file so they can be audited and reused. The founder's own hard invariants still stand — the terrorist-organisation block, Qur'an text integrity, licence posture, safety gates — unless the founder lifts them explicitly; everything else in the decision space is delegated.

- **Own the museum's completeness and growth (founder delegation, 8 November 2026).** A standing mandate: completely enrich the prose and the website, and grow the website continuously. Do not wait to be told what is missing — figure out what else needs to be done, shown, added, revised, cleaned, enhanced, better displayed or refined: audit coverage gaps (entities without prose, stale stubs, missing translations, thin summaries, unmined sources), usability and accessibility gaps, display and navigation improvements, new content classes or browsers the graph can support, and quality defects. Then do the work: rich first-pass prose in all three languages, cited and provenance-stamped, validated and pushed in small batches. The goal is compounding: more context, more usability, more cross-linking — until islam.museum is the most useful and most referenced website about Islam on the global web. Every addition still cites defined sources, follows the voice and scope rules, and lands through the same gates (validate, test, CANARY, decision ledger for judgment calls).

- Several agents work in parallel. **Never ignore, discard or revert another agent's work.** Fetch and review what is new on `origin/main` before you start and before every push, then merge it with yours; duplicates become aliases; nothing is deleted blindly.
- One git worktree or clone per session, never a shared folder; commit explicit paths (never `git add -A`); never force-push; never commit `node_modules`, PDFs, OCR text, page images or large files.
- Push small, validated commits often (work can be lost if you run out of credit or time), and keep your lane's progress file current. **Since 22 October 2026 `main` accepts pull requests only** (a repository ruleset blocks direct pushes, force-pushes and deletion, with no bypass): push your branch and open a pull request; agents merge their own PRs after fetching and three-way merging `origin/main` (dec-20261108-185); the Validate workflow runs the tests and the build on every pull request. See `docs/agents/workflow.md` section 4.
- Shared files (`data/_stubs.yaml`, `data/_stubs.d/*`, `docs/status.md`, enums) are append-only: never replace one wholesale. Your own stubs go in your own `data/_stubs.d/<lane>.yaml`.
- **Every agent commit ends with attribution trailers** `AI-Agent:`, `AI-Model:` and `AI-Editor:` (truthful; `unknown` if you cannot tell), and the same facts go in each entity's provenance. See `docs/agents/workflow.md`.
- **Totals stay current.** Every check-in that changes entities, stubs or edges regenerates `docs/coverage.md` with `npm run coverage` in the same commit (never hand-edit it). See `docs/agents/workflow.md` section 4.
- Commit and push validated work without waiting for anyone's sign-off (founder's standing permission, `docs/sources-policy.md` §5); conventional commit messages; at most 25 entities per content batch.
- **One branch: `main` (founder rule, 12 November 2026).** Every pull request is raised against `main`. No pull request is raised against `release/uat` or any other release branch any more, and nothing is merged into one. Both environments are deployed from `main`: production (`deploy.yml`) and UAT (`deploy-uat.yml`, leaving `source_branch` at its default, `main`). `release/uat` was merged into `main` on 12 November 2026 and is retired; work found there is brought to `main` by a pull request to `main`, never the other way.
- **Deployment is manual and the founder's alone (since 21 October 2026).** A push to `main` publishes nothing: the Cloudflare workflow (build, R2 publish of HTML, search and API, Worker deploy, Pages) runs only when the founder starts it, normally once a day once enough has landed, to keep R2 and build costs down. No agent or session runs `deploy.yml` or `deploy-uat.yml` (not `gh workflow run`, not the Actions tab, not a push trigger). Since 1 November 2026 the founder can first deploy the same build to the UAT copy of the hosting (`deploy-uat.yml`, `https://uat.islam.museum`, its own bucket, Workers and Pages project, never indexed) and then to production with the same `build_run_id`; the two workflows share one procedure (`deploy-env.yml`) and differ only by GitHub Environment (`docs/engineering/06-deployment.md` section 8). When your work needs to be live, say so in chat: name the commits, what changed and whether a Worker or workflow file is among them, and the founder deploys. Everything else stays as it is: run the checks locally before every push (`npm run validate`, `npm test`, `npm run build` for site changes), open a pull request if you want CI to run them (`validate.yml`). See `docs/agents/workflow.md` section 9.
